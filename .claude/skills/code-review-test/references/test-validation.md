# 테스트 검증 절차

작성하거나 검토한 테스트 자체가 믿을 만한지 확인한다.

1. 테스트가 요구사항의 어떤 계약을 검증하는지 한 문장으로 정의한다.
2. 수정 전 결함에서 실패하고 수정 후 통과할 이유를 확인한다.
3. assertion을 제거하거나 잘못된 결과를 반환했을 때 실패하는지 검토한다.
4. production 메서드를 과도하게 mock해 항상 통과하는 테스트가 아닌지 확인한다.
5. 경합 테스트의 실행 순서가 Event 또는 barrier로 보장되는지 확인한다.
6. sleep과 머신 속도에 따라 결과가 바뀌지 않는지 확인한다.
7. 생성한 background task와 resource가 성공·실패 모두에서 정리되는지 확인한다.
8. 단독 실행과 관련 테스트 묶음 실행에서 같은 결과인지 확인한다.
9. 가능하면 해당 테스트를 반복 실행해 flakiness를 확인한다.
10. Windows와 CI 등 플랫폼 차이를 고려한다.
11. 환경 실패(DB 미기동, 권한, 경로, 포트 등)와 assertion 실패를 구분한다.
12. skip 또는 xfail이 실제 결함을 숨기지 않는지 확인한다.

## 결함 주입 확인
- mutation test 도구나 새 패키지는 설치하지 않는다.
- 필요하면 테스트 대상 함수를 monkeypatch해 의도적으로 잘못된 결과를 반환하게 하고 테스트가 실패하는지 확인할 수 있다. 이 변경은 테스트 프로세스 안에서만 수행하며 파일을 수정하지 않는다.

## 반복 실행
- 합리적인 횟수(예: 수 회~수십 회)로 제한한다.
- 실제 외부 CLI 테스트에는 적용하지 않는다.
